# SSA saved-application development extension

This separate Manifest V3 package recognizes the active tab's URL when the employee opens its popup. The **Open SSA application** button in Intake Assistant asks this extension to open `https://secure.ssa.gov/iClaim/dib` in a new tab. The employee enters a re-entry number temporarily in Intake Assistant; a unique ready SSN comes from the Checker-owned profile. Both are sent only through Chrome extension messaging and kept in extension service-worker memory for at most five minutes. On the observed SSA flow, this opens the Terms of Service page; the employee must review the agreement and click Next. The extension then attempts to select the unique **Return to Saved Application Process** control and fill the two exact identity fields. It does not click Next on the identity page, fill application answers, or submit an application. Do not enter real client information during development tests.

Install in Chrome from `chrome://extensions` → Developer mode → Load unpacked → this folder. It has a different extension ID from the synthetic practice extension and can be installed alongside it. Reload here after changes. Use a test browser profile for development. Staff distribution and browser policy approval are separate decisions.

The permissions are `activeTab`, `scripting`, and one HTTPS host (`secure.ssa.gov`). `externally_connectable` allows Toolkit pages to contact the extension, while the service worker accepts only exact supported Intake Checker URLs and a top-level source tab. It rejects extra fields and invalid identity messages. The extension inspects only SSA pages under `/iClaim/`, requires exact visible page headings and controls, and pauses when controls are missing, repeated, already filled, or changed. No Terms checkbox is selected. There is no storage, cookie, content-script, database, log, analytics or third-party data service. Toolkit authentication remains in Toolkit; no cookie or token is sent to the extension. URL recognition is not a verified application-question mapping.

Only synthetic tests have been run for the identity flow; the real SSA controls have not been verified against their page markup. The extension clears the identity values after an attempted fill, on Back, source-tab reload/close, disconnect, authentication loss, target-tab close, or five-minute expiry. If the controls do not match, the employee continues manually. The re-entry number is not derived from the intake and never enters Toolkit preferences. Application-answer filling remains disabled because no live question mappings have been verified. MFA, CAPTCHA, signatures, penalty-of-perjury confirmations, and final submission remain manual.

## Planned client-profile boundary

The popup still offers the separate navigation-only test. The Toolkit button is the only path that sends the two identity values. Its short-lived session does not infer a successful login from page contents. Later application pages pause because the verified field registry is empty.

The existing Toolkit-to-synthetic-practice bridge remains separate. Future application-answer transfer must send only explicitly approved, ready field IDs and values from the Checker-owned profile. It must never include raw intake text, source snippets, review logs, or blocked values. Each SSA page/question mapping must be verified before filling; unsupported or changed questions pause for manual handling. No data storage, analytics, or external service is permitted.

`live-mappings.js` contains an empty registry and a ready-field projection guard for that future bridge. It has no SSA selectors and is not connected to Toolkit or the page. Its registry stays empty until the first page is verified. Authentication and re-entry targets are reserved from future automatic mapping.

`live-session.js` separately provides a future in-memory, one-tab, five-minute boundary for application answers. It rejects absent approval, unknown profile versions, other tabs, other origins, changed page keys and expired sessions. It stores only planned ready values, not the input profile; currently that list is empty. Neither application-answer module is connected to the current identity session.
