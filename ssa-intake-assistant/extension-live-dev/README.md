# SSA saved-application development extension

This separate Manifest V3 package recognizes the active tab's URL when the employee opens its popup. The **Open SSA application** button in Intake Assistant can now ask this extension to open `https://secure.ssa.gov/iClaim/dib` in a new tab. That launch request contains no client data. On the observed SSA flow, this opens the Terms of Service page; the employee must review it and continue manually. The extension does not receive an Intake Checker profile, fill an SSN or re-entry number, fill application answers, or submit an application. Do not enter real client information during development tests.

Install in Chrome from `chrome://extensions` → Developer mode → Load unpacked → this folder. It has a different extension ID from the synthetic practice extension and can be installed alongside it. Reload here after changes. Use a test browser profile for development. Staff distribution and browser policy approval are separate decisions.

The permissions are `activeTab`, `scripting`, and one HTTPS host (`secure.ssa.gov`). The existing popup test control can attempt one exact saved-application click on the landing URL, but it has not been verified on the observed Terms page. The Toolkit button does **not** inject a script or click a page control. `externally_connectable` allows Toolkit pages to contact the extension, while the service worker accepts only the exact supported Intake Checker URLs, a source tab, and a launch-only message with no extra fields. There is no storage, cookie, content-script, or Toolkit profile permission. No form values, credentials, authentication cookies, tokens, or client profiles enter the extension. URL recognition is not a verified question mapping.

Only synthetic tests have been run for this launcher. The live SSA flow has not been verified by an automated browser test. On the observed pages, the employee reviews and accepts the Terms of Service, selects **Return to Saved Application Process**, and enters the SSN and re-entry number directly on SSA. Next milestones require verified page markup and separate tests before live field filling. Credentials, re-entry numbers, MFA, CAPTCHA, attestations, signatures, penalty-of-perjury confirmations, and final submission remain manual.

## Planned client-profile boundary

The popup shows the three stages: open the saved application, complete SSN/re-entry and any identity steps directly on SSA, then review application questions. It does not try to infer completion of the identity stage from page contents. There is no SSN or re-entry-number input, store, message, or profile receiver in this extension.

The existing Toolkit-to-synthetic-practice bridge is **not** a live-client bridge: it requires an employee declaration that the intake is fictional. A later live bridge must have a separate extension identity and channel, keep Toolkit authentication in the Toolkit tab, and send only explicitly approved, ready field IDs and values from the existing Checker-owned profile. It must bind the approval to one SSA tab and one short-lived session, clear on Back, correction, logout, tab close, disconnect, or timeout, and never include credentials, re-entry numbers, raw intake text, source snippets, review logs, or blocked values. The extension must not fill anything until each SSA page/question mapping is verified and approved. Unsupported or changed questions pause for manual handling. No data storage, analytics, or external service is permitted.

`live-mappings.js` contains an empty registry and a ready-field projection guard for that future bridge. It has no SSA selectors and is not connected to Toolkit or the page. Its registry stays empty until the first page is verified. Authentication and re-entry targets are reserved from future automatic mapping.

`live-session.js` provides a future in-memory, one-tab, five-minute boundary. It rejects absent approval, unknown profile versions, other tabs, other origins, changed page keys and expired sessions. It stores only planned ready values, not the input profile; currently that list is empty. Neither module is connected to a transport, Toolkit, or a live page.
